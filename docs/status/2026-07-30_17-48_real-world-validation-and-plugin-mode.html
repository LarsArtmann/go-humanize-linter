Critical

H004 was shipped with ~60% false positive rate

patterns.go:489 hasEqualsOneBranch — original version

The original H004 fired on ANY if x == 1 where x was a simple identifier. This matched percentile calculations (if n == 1 { return sorted[0] }), SQL health checks (if result != 1 { return fmt.Errorf(...) }), exit-code extraction, IBAN validation, database readiness checks, and code generation. Of 44 findings, ~29 were false positives. The rule was essentially useless as shipped.

Fixed this session: Two-stage filter: (1) branch body must contain a string literal/concatenation, (2) function must return string type. Result: 44 → 24, ~0% FP.
Critical

H001 reports "0 unit strings" when triggered by div1024 alone

rule_bytes.go:37 detectBytesFormat — message construction

The KMGTPE testdata ("%.1f %cB" with "KMGTPE"[exp]) embeds unit strings inside format strings, not as standalone strings. countByteUnits() uses \b word boundaries on extracted string literal values, but "%.1f %cB" doesn't contain literal "KB" or "MB" — the unit is assembled at runtime via %cB. So the message says "0 unit strings, div1024=true" which is confusing and technically wrong — the function IS formatting bytes, the detector just can't see the unit strings because they're constructed dynamically.

Still broken: The message should say something like "KMGTPE index trick detected" instead of "0 unit strings" when kmgtp=true.
Critical

Plugin reports ALL findings at function declaration line, not the actual code line

plugin/plugin.go:79 — uses fn.Pos() unconditionally

toDiagnostic() uses fn.Pos() (the func keyword position) for every finding. If a 50-line function has byte formatting on line 30 and comma formatting on line 40, both are reported at line 1 (the func declaration). The finding.Position has the correct line/column from the detector, but the plugin ignores it. This makes the plugin nearly useless for IDE integration — you can't jump to the actual code.

Still broken: Need to either store the AST node position in the finding or reverse-map finding.Position to token.Pos via pass.Fset.

EWhat We Should Improve

1. H004 should require string output in BOTH branches, not just the == 1 branch

Current logic: branchContainsString(ifStmt.Body) checks the == 1 branch only. But true pluralization has strings in BOTH branches (singular AND plural). The waveLabel borderline false positives pass because the else branch also has strings. Requiring both branches to have strings would be stricter but might miss some patterns. Consider: require strings in the function body overall (already done) OR in the specific branch (current approach).

2. Plugin position mapping is fundamentally broken

The plugin must map finding.Position{File, Line, Column} back to a token.Pos for pass.Report(). Options: (a) store the AST node position in the finding (adds a field or metadata), (b) use pass.Fset.File(file.Pos()).LineStart(line) + token.Offset(col-1) to reverse-map, or (c) have detectors return token.Pos alongside findings. Option (c) is cleanest but requires API change.

3. patterns.go is still 850+ lines and growing

Every new detection helper goes into the same file. Should split into: pattern_bytes.go (H001), pattern_comma.go (H002), pattern_time.go (H003), pattern_plural.go (H004), pattern_si.go (H005), pattern_ftoa.go (H006), pattern_parsebytes.go (H007), pattern_helpers.go (shared).

4. No --version flag on CLI

Standard CLI practice. Should be --version that prints the module version (injectable via -ldflags "-X main.version=...").

5. H001 confidence calibration is off for the "0 unit strings" case

When kmgtp=true and unitCount=0, confidence is set to ConfidenceFull (correct — KMGTPE index is a slam dunk) but the message says "0 unit strings" which makes it look like a weak signal. The message and the confidence disagree.

6. No CI test for the plugin path

The plugin's run() function requires a real analysis.Pass which needs package loading. The integration test should use analyisttest or analysistest.testing to verify the plugin produces correct diagnostics on testdata packages. Currently only the exported DetectFuncDecl is tested.

7. Self-detection: linter flags its own rule_bytes.go

go-humanize-linter/rule_bytes.go:37 is flagged as H001 because it contains byte-unit string literals and division-like patterns in the detection code itself. Should add the linter's own source to an ignore list, or add //nolint:gohumanize directive support.

8. No nolint directive support

Users can't suppress false positives with //nolint:gohumanize or similar. Standard linter feature. The CLI and plugin both need this.

9. Sweep results should be saved as a report artifact

The JSON output from the full ~/projects/ sweep was written to /tmp/hlint-results-v3.json which will be deleted. Should save a snapshot to docs/validation/ for tracking FP rate over time.
