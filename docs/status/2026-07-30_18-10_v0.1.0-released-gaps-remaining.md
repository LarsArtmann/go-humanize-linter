## e) WHAT WE SHOULD IMPROVE

### Architecture

1. **Detectors should return `token.Pos` alongside findings.** Currently every finding reports at the function declaration position. To get per-line diagnostics (critical for IDE/golangci-lint usability), each detector function needs to identify the specific AST node that triggered the finding and return its position. This is a moderate API change but the single highest-impact improvement.

2. **`DetectFuncDecl` needs core test coverage.** It's the shared entry point for both CLI and plugin, but has 0% coverage in the core package. A single test in `linter_test.go` calling `DetectFuncDecl` with a known-positive fixture would close this gap.

3. **Plugin needs `analysistest` integration.** The plugin's `run()` function requires a real `analysis.Pass` with loaded packages. Using `golang.org/x/tools/go/analysis/analysistest` would test the full pipeline (file → pass → diagnostics) and bring plugin coverage from 6.2% to 80%+.

### Testing

4. **CLI functions are testable but untested.** `buildRegistry()`, `output()`, and `stringList` can all be unit-tested without exec'ing the binary. Extract them to a non-`main` package or use internal testing.

5. **6 functions have <50% coverage.** `exprIsStringy` (0%), `isStringType` (40%), `plugin.run` (0%), `plugin.isGenerated` (0%), `cmd/gohumanize/main` (0%), `cmd/go-humanize-linter/main` (0%). Each needs targeted tests.

### UX

6. **No `//nolint` support.** Every linter needs this. Without it, users who hit a false positive have no recourse except disabling the entire rule. This is the #1 adoption blocker.

7. **Self-detection.** The linter flags its own `rule_bytes.go` as H001 because the detection code contains byte-unit patterns. This is expected but embarrassing. Either add self-exclusion or add a `//nolint:gohumanize` comment (once nolint support exists).

8. **No SARIF integration test.** SARIF output is implemented but never tested via CLI. If `report.WriteSARIF()` breaks, nobody will know until a CI pipeline fails.

### Process

9. **Status report accuracy.** Session 2's status report overstated the plugin position issue as "critical" when it's actually consistent behavior. Future status reports should verify claims against actual behavior before classifying severity.

10. **golines is dangerous on hand-formatted code.** The `golines -w` command extracted phantom functions from rule_bytes.go. Should use `gofmt` only, or `golines --dry-run` first to check the diff.

## g) Questions I Cannot Answer Myself

### Q1: Should the linter auto-fix findings, or only suggest?

The go-finding pipeline has a `FixEngine` that can apply fixes programmatically. Auto-fixing `formatBytes()` → `humanize.Bytes()` sounds great but is dangerous — the function signature, call sites, and import must all change atomically. Should I build auto-fix for v0.2, or keep it suggest-only indefinitely? This depends on your risk tolerance for automated code changes.

### Q2: Do you want a public documentation website?

The `website-launch` skill can deploy an Astro + Starlight + Firebase Hosting docs site at `lars.software`. Your other Go projects (go-output, go-finding) — do they have public doc sites, or is README + godoc sufficient for this project? I can't tell from the codebase alone whether you consider a website worth the maintenance overhead.

### Q3: How aggressive should new rules be?

H001-H007 are conservative (require 2+ signals, ~0% FP). I could add H008 (ordinal), H009 (commaf), H010 (lookup), but each new rule increases the surface area for false positives. Should v0.2 prioritize more rules (breadth) or improving existing rules with type information (depth)? This is a product direction question I can't answer myself.
