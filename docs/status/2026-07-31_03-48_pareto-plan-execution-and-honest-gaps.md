## G. Questions

### Q1: Should I debug and fix the golangci-lint v2 module plugin registration before we tag v0.2.0?

The `custom-gcl` binary builds but doesn't discover `gohumanize` at runtime. This could be a `.custom-gcl.yml` config issue, a `register.Plugin` API mismatch, or a golangci-lint v2 version incompatibility. Debugging this is the difference between "plugin works in theory" and "plugin works in practice." **However**, the CLI path (standalone binary) is fully functional and tested — the plugin is an adoption convenience, not a correctness requirement.

### Q2: Should the CHANGELOG entries for this session go under `[0.2.0]` or a new `[Unreleased]` / `[0.3.0]` section?

The `[0.2.0]` section already exists and documents the previous session's work. These new features (configurable plugin, import aliases, package-level vars, `--config`, GitHub Action) are arguably v0.2.0 features since v0.2.0 hasn't been tagged yet. But they could also be v0.3.0 scope if you want to tag v0.2.0 as-is.

### Q3: Should I update all living docs (TODO_LIST, CHANGELOG, FEATURES, AGENTS.md) right now, or wait until the plugin registration is verified?

If the plugin registration turns out to be fundamentally broken and needs a different approach, the docs would need to be re-written. Updating docs now risks a second round of edits. But NOT updating them means the trophy-case problem persists for another session.
